# Contributing to Edge Voice

These rules apply to everyone working in this repository, people and coding agents alike.

## Setup

```bash
bun install          # also installs the git hooks (lefthook)
bun run sandbox      # build, open the sandbox, and reload the plugin on every change
```

Use the Bun version pinned in `package.json` (`packageManager`). Install Obsidian locally to use the macOS sandbox and real Obsidian tests.

The Python checks need [uv](https://docs.astral.sh/uv/), and commits need [gitleaks](https://github.com/gitleaks/gitleaks) (`brew install gitleaks`, or a release binary), which the pre-commit hook runs on what's staged.

### The sandbox

`bun run sandbox` opens a second Obsidian, separate from your own, with a vault of sample notes and PDFs and the plugin built from this folder. Each change rebuilds it and reloads the plugin there. Your everyday Obsidian, its settings and vaults are never touched, so don't link this folder into a vault you use. It runs on macOS for now; elsewhere, link the folder into a test vault (`ln -s "$PWD" <vault>/.obsidian/plugins/edge-voice`) and use `bun run dev`.

| Command                           | What it does                                                                                    |
| --------------------------------- | ----------------------------------------------------------------------------------------------- |
| `bun run sandbox`                 | Build, open the sandbox (or reload the plugin if it's open), and keep reloading on every change |
| `bun run sandbox --fresh`         | The same without your engine, so the plugin shows its setup steps as for a new user             |
| `bun run sandbox --python <path>` | Use this Python for the engine, and remember it                                                 |
| `bun run sandbox:reset`           | Put the sample notes and PDFs back                                                              |
| `bun run sandbox:errors`          | Errors from the sandbox, for you or a coding agent                                              |

The sandbox lives in `.sandbox/` (gitignored): its own Obsidian profile, its own `HOME`, and the vault. It shares your speech engine and voices (`~/.edge-voice/engine` and `hf`, and Moonshine's voice cache) through links, so nothing downloads twice. It drives Obsidian through `obsidian-cli`, which comes with Obsidian (checked with 1.14); the sandbox turns it on in its own profile only, and keeps it away from your keychain (`--use-mock-keychain`). The samples are in `sandbox/notes/`, and the PDFs are generated by `scripts/sandbox/pdfs.ts`.

## Checks

| Command                 | What it does                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| `bun run check`         | Type-check, lint, format check, Vitest and pytest; excludes build and real Obsidian            |
| `bun run typecheck`     | TypeScript, including tests                                                                    |
| `bun run lint`          | ESLint with Obsidian's community-review rules (`eslint-plugin-obsidianmd`)                     |
| `bun run format`        | Prettier for TypeScript, CSS, JSON and Markdown; ruff for Python                               |
| `bun run format:check`  | The same, checking only                                                                        |
| `bun run test`          | Vitest: text processing, PDF reading (generated PDFs), sidecar protocol, storage               |
| `bun run test:python`   | pytest: the engine (`engine/`) against a stub of moonshine-voice                               |
| `bun run build`         | Type-check and bundle `main.js`                                                                |
| `bun run test:obsidian` | The tests against real Obsidian (opens a test Obsidian for a few seconds; not part of `check`) |

`bun run check` does not run `bun run format`, `bun run build` or `bun run test:obsidian`. CI runs the same checks plus a production build; secret scanning runs in a separate job. Run `bun run build` for changes to shipped code, bundling or dependencies.

CI also runs Bandit 1.8.6 via uvx over every Python file in `engine/` and `scripts/`. Suppressions name a single check at a single expression, with the reason beside it; new findings fail CI. The Hugging Face revision suppression has a separate full-commit check. Raw findings are uploaded as `bandit-report`.

### Dependency advisories

The **Dependency advisories** workflow runs weekly, by hand, and on pull requests changing its scanner or lock inputs. Start it with `gh workflow run advisory-scan.yml --ref <branch>`. If GitHub cannot resolve a new workflow by filename before merge, use its numeric workflow ID from a PR run instead. Read the run summary and download the `dependency-advisories` artifact for raw JSON and diagnostics.

To run the same report locally:

```bash
uv run --no-project --python 3.12 scripts/audit-dependencies-test.py
uv run --no-project --python 3.12 --with pip-audit==2.10.1 scripts/audit-dependencies.py --enforce-policy
```

Reports go to `.scratch/security-audit/`. The scanner queries every `locks/*.txt`, including MLX, using pinned pip-audit with `--disable-pip --require-hashes`, and runs `bun audit --json` over all of `bun.lock`, including development dependencies. It queries advisory services with package names/versions; it does not install engine/model packages, validate artifact contents, change locks, apply fixes or open update PRs. Bun and uv must be available locally. Network access is required.

Advisories, skipped/unmapped packages and scanner errors are reported separately. The repository-built edge-voice-engine, docopt and Mac Moonshine wheels remain explicit coverage gaps even when a PyPI name/version query succeeds; bundled native libraries and externally downloaded model assets need separate review. A missing result, skipped package or failed query must not be interpreted as a clean audit. With policy enforcement, exit 1 means an unaccepted advisory; exit 2 means a scanner/input/policy error. Documented gaps and current dated dev exceptions stay visible without making the job fail. Unfiltered reporting without --enforce-policy retains its conservative nonzero result for findings or gaps. Reports are uploaded even for nonzero results. A maintainer reviews findings and proposes any dependency changes separately; the scheduled/PR report enforces the same reviewed policy as releases. Plugin and engine releases run the scanner with `--release` (an alias of `--enforce-policy`): every engine-lock advisory or scanner failure blocks publication. Only the exact moderate-or-lower dev advisories in `scripts/advisory-allowlist.json` can pass, with a reason, review date and expiry. Review it by its `reviewBy` date; an expired policy blocks releases. Adding production Bun dependencies disables these dev-only exceptions until their scope is reviewed. Coverage gaps remain visible and are not audited passes.

Use `bun run test`, not `bun test`: the latter is Bun's own test runner, not Vitest.

The pre-commit hook formats and lint-fixes staged files and type-checks; the pre-push hook runs both test suites. Don't skip them (`--no-verify`) except to commit work in progress on a branch of your own.

## Testing a change

Four layers, each catching what the one before can't:

1. **`bun run check`** (run in CI; hooks run subsets): the text rules, PDF reading, the sidecar protocol, the setup steps and engine search, the engine against stubs (pytest), and behaviour: playback on a fake clock with a fake voice (`tests/support/playback.ts`), what play/pause does (`src/controls.ts`), and the player bar in a fake page (`tests/support/obsidian-dom.ts`). New behaviour gets a test here; a fix gets a test that failed before it.
2. **The sandbox, by hand:** how it looks, sounds and behaves in Obsidian, which no test sees. Keep `bun run sandbox` running while you work, try the change there, and check `bun run sandbox:errors` reports none.
3. **Real Obsidian, automated** (`tests/obsidian/`, `bun run test:obsidian`): a throwaway sandbox (`.sandbox-test/`) with the plugin built from your tree and a fake engine, driven through `obsidian-cli`. It checks what only real Obsidian shows: its internals (Reading view's sections, the editor) and its styles. The **Obsidian** workflow runs it before every release, and by hand from the Actions tab. Locally it opens a test Obsidian for about ten seconds, so run it when you change how the plugin meets Obsidian.
4. **CI on other platforms:** what nobody can try on one computer (below).

What to try in the sandbox, by what you changed:

| Change                                          | Try                                                                                                                                                                                                                                  |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Reading, skipping, speed, highlighting in notes | Read `Markdown features` in Source mode, Live Preview and Reading view, and switch modes mid-sentence. In `A long note`, skip forward and back, pause, resume and change speed.                                                      |
| Text rules (`src/normalize.ts`)                 | Listen to `Numbers and units`, and add a line there for the case you changed, so the next person hears it too. A rule is checked against how the voice actually says it.                                                             |
| PDFs (`src/pdf.ts`)                             | Open both files in `PDFs/`: headers, page numbers, the margin stamp and the footnote are skipped (the footnote is read if _Skip footnotes in PDFs_ is off); the two columns read in order; the highlight follows onto the next page. |
| Player bar, status bar, settings                | Both light and dark themes (Settings → Appearance in the sandbox), and a couple of highlight colours.                                                                                                                                |
| Double tap, pausing in the background           | Switch notes; hide Obsidian (⌘H), minimize it, cover it with another window.                                                                                                                                                         |
| The engine (`engine/`) or the sidecar           | Read a note and a PDF. `bun run sandbox:errors` shows errors the plugin raised; the sidecar's own output is in the sandbox's developer console (⌥⌘I, with Verbose shown).                                                            |
| Setup (`src/engine.ts`, `engine/`, `locks/`)    | `bun run sandbox --fresh` shows the setup steps, as for a new user. Running them needs a downloadable engine release (public repository); until then, build one with `scripts/build-engine-release.sh` and point step 3 at it.       |

Other platforms, in CI: the **Engine package** workflow builds an engine release and, on each platform (macOS Intel and Apple silicon on 14 and 15, Windows, Linux x64 and ARM), runs the exact setup steps Edge Voice shows (`scripts/setup-steps.ts`), downloads a real voice with step 4, and has the engine speak with the network cut off (`scripts/engine-speaks.py`); the faster engine does the same on Apple silicon. It runs on pull requests touching `engine/`, `locks/`, `src/engine.ts` or its scripts, and can be started by hand from the Actions tab.

Every bug gets a test at the cheapest layer that catches it: a unit test if it can, real Obsidian if only Obsidian shows it.

In the pull request, say what you tried by hand, where, and what still needs a person: another platform, a real Apple silicon GPU, a screen reader.

## Rules

**Code**

- Formatting is whatever Prettier and ruff produce. Tabs in TypeScript and CSS, 120 columns.
- Lint errors fail CI. Warnings are allowed only where `eslint.config.mjs` explains why.
- No `any`: type what crosses a boundary (`JSON.parse`, `loadData`, pdf.js, the sidecar protocol).
- Comments say why, not what. Match the density of the code around them.
- UI text is in sentence case, plain English, and names no internals the reader doesn't need.
- Use window timer APIs for browser code; use the owning window for DOM work in pop-out windows; register listeners and events through the plugin (`registerDomEvent`, `registerEvent`) so they're removed on unload.
- No secrets in the repository: no tokens, keys or passwords, not even in tests. gitleaks checks each commit, and CI scans the whole history. If it flags something that isn't a secret, add it to a `.gitleaksignore` with the reason in the commit message.

**Behaviour**

- The plugin downloads and installs nothing, ever: no programs, packages or voices. When something is missing it shows a command for the person to run, with what it does and where its downloads come from. The engine it runs reads only what's on disk (moonshine-voice with `download=False`, Hugging Face offline). Only the commands the person runs download: uv's Python, the engine release's packages, and voices (`edge-voice-engine voices get`, from Moonshine's server and, with `--faster`, Hugging Face). Don't add network calls or telemetry.
- The engine is the `edge-voice-engine` package (`engine/`), which people install from an engine release; the plugin runs it as `python -I -u -m edge_voice_engine`. Keep it to the standard library plus moonshine-voice (and the faster engine's packages), and keep its JSON-lines protocol backward compatible within a protocol version (`PROTOCOL`). Document new requests in its docstring. Changing the engine's version means changing `VERSION` and `engine/pyproject.toml` together; a test checks they agree.
- Text normalization rules (`src/normalize.ts`) must be checked against the engine's pronunciation before they're added. Add a test with the written form and the spoken form.
- The engine is replaceable: keep engine specifics in `engine/` and `src/engine.ts`, out of the reader, sources and UI. Setup commands shown to people must stay readable and unalarming: no `sudo`, no piping downloads into a shell, every input a file people can read first.

**Tests**

- New behaviour comes with a test. Fixes come with a test that failed before the fix.
- Tests don't use third-party documents without permission or a suitable license. Build what you need, as `tests/pdf.test.ts` builds its PDFs with pdf-lib.

## Commits and branches

- `main` is always releasable. Work on a branch and open a pull request; CI must pass before merging.
- Commit messages: a short imperative summary line ("Skip footnotes in PDFs"), then a blank line and the why, when it isn't obvious.
- User-facing changes get a line in `CHANGELOG.md` under _Unreleased_.

## Releases

For Community directory submission, check against the current [developer policies](https://docs.obsidian.md/community-directory/developer-policies), which prohibit plugins installing or updating their dependencies. Edge Voice installs and downloads nothing itself; people set up the engine with commands it shows, as two community answers to our forum question suggested. No answer from the Obsidian team yet, so don't claim directory compliance.

Only perform these steps when a maintainer has authorized a release. Start with a clean working tree and passing checks.

The Release workflow builds and tests with read-only repository permissions. Only its final publishing job has `contents: write`; it downloads the named artifact from that same run and drafts the release without checking out or executing project code. A manual run (`gh workflow run release.yml --ref <branch>`) checks the build, real Obsidian gate and a separate read-only artifact download without publishing. For a repeated artifact-only validation, pass `-F run-obsidian=false` to avoid spending more macOS minutes; tag releases always run the Obsidian gate. The download check lists and verifies the release files and their SHA-256 checksums without checking out or executing project code. The Engine wheels workflow also defaults to build/test only: explicitly enable its **publish** input only when a wheel release is authorized.

Third-party actions are pinned to full commit SHAs with release versions in comments, selected from releases at least two weeks old. Weekly Dependabot checks propose GitHub Actions updates; maintainers must verify release age and the referenced commit before merging an update.

1. Move the _Unreleased_ entries in `CHANGELOG.md` under the new version.
   Commit the changelog change before running the version script; the script only stages the three version files.
2. `bun run release 0.2.0` (updates `package.json`, `manifest.json` and `versions.json`, commits and tags `0.2.0`).
3. Push the release commit to the intended branch and the specific version tag explicitly, for example `git push origin main` and `git push origin 0.2.0` after the release commit is on `main`. The script creates a lightweight tag, which `--follow-tags` does not push. The release workflow builds and attaches `main.js`, `manifest.json`, `styles.css` and `SHA256SUMS` to a draft GitHub release; check it and publish it.

**Engine locks.** Engine releases install from `locks/<platform>.txt`: every package, dependencies included, at exact versions with their hashes. After changing moonshine-voice's version, the Mac wheels or the faster engine's packages in `engine/pins.json`, run `scripts/lock-engine.sh` (needs uv and gh) and commit the locks; it checks the Mac wheels and spaCy's model against the checksums in `pins.json` first, and the tests fail if the locks or `engine/pyproject.toml` disagree with it. The locks only take releases at least two weeks old.

The lock generator preserves existing output pins; pass `--upgrade-package <name>==<version>` for a targeted refresh, then review every changed version and hash. For an urgent security fix younger than two weeks, obtain maintainer approval and record the package, version and release timestamp in the PR. Pass a narrowly scoped `--exclude-newer-package <name>=<timestamp>` exception alongside the exact upgrade; keep the global two-week cutoff for everything else.

**Voice hashes.** With the current platform lock installed, run `python scripts/lock-voices.py --cache .scratch/voice-lock-cache --refresh` when reviewing a voice/catalog update (network required). It hashes every English Kokoro/Piper dependency, including shared language files, and records faster-engine files at the full Hugging Face revision pinned in the server. Review the source revision, hashes and sizes; initial Moonshine hashes are captured from its HTTPS host, not independently signed upstream metadata. Commit both `engine/voices.json` and its identical packaged copy at `engine/src/edge_voice_engine/voices.json`; run Prettier on both. The maintenance cache is gitignored. The normal `voices get` command rejects unlisted voices unless the person explicitly uses `--unverified`, warns for that opt-in, and still verifies known files. A mismatch removes the affected cache file and fails; retry the command to fetch a replacement. Serving the plugin stays offline without re-hashing on every load.

**Engine releases.** The engine is also the `edge-voice-engine` package (`engine/`), which people install themselves from an `engine-<version>` release with two uv commands (`uv venv` then `uv pip install --require-hashes`; `uv tool install` can't check hashes). The release generator verifies every requirements file against exactly its base/MLX lock versions plus the engine version, including wheel URLs and required extras; fixture-wheel regression tests run in Engine package CI. The release carries the engine wheel, the Mac wheels, a docopt wheel (PyPI only has its source) and one requirements file per platform: the lock plus those wheels by URL, every line with its hash. We never publish to PyPI, and the requirements name our packages by URL, so a same-named package there can't stand in. `scripts/build-engine-release.sh` builds all of it; the _Engine package_ workflow builds it on pull requests that touch the engine or the locks, serves it locally and runs the setup steps on every platform. To release, bump `VERSION` in `server.py`, `engine/pyproject.toml` and `ENGINE_VERSION` in `src/engine.ts` together (tests check they agree), then run _Engine release_ with **publish** ticked (maintainers only). The notes carry the setup steps for each platform and the checksums. Downloads work only once the repository is public.

**Engine wheels for macOS.** PyPI has no moonshine-voice wheel for Intel Macs, and its Apple Silicon one needs macOS 15, so engine releases carry wheels this repository builds instead. When moving to a new moonshine-voice version, run the _Engine wheels_ workflow (Actions → Engine wheels → Run workflow) with the moonshine tag that matches the PyPI version. It publishes a `moonshine-voice-<version>` release; copy the release name, asset names and checksums from its notes into `moonshine` in `engine/pins.json`, then run `scripts/lock-engine.sh`.
